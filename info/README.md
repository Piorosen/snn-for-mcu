# STM32F746G-DISCO 하드웨어 정보 수집

이 폴더는 **이 프로젝트가 쓰는 보드가 물리적으로 어떤 물건인지**를 가능한 모든 방법으로
조사한 결과다. 데이터시트를 옮겨 적은 것이 아니라, **보드에 직접 물어본 값**을 1차 자료로 삼고
공식 문서를 그 위에 얹었다. 둘이 어긋나는 지점이 여러 군데 발견되었고, 그 경우 실측을 따랐다.

- 대상 보드: STM32F746G-DISCO (MB1191)
- 실장 MCU: STM32F746NGH6 — Cortex-M7 r0p1, Device ID `0x449`, Revision **Rev Z** (실측 확정)
- 조사일: 2026-07-27

---

## 신뢰도 등급

모든 사실에는 등급이 붙어 있다. 등급이 다르면 근거의 성격이 다르다는 뜻이다.

| 등급 | 의미 | 근거 |
|---|---|---|
| **A-1** | 이 보드에서 ST-LINK로 레지스터를 직접 판독 | 실리콘이 답한 값 |
| **A-2** | 이 보드에서 실행한 프로브 펌웨어가 측정 | 칩이 스스로 측정한 값 |
| **B** | ST/ARM 공식 문서 또는 벤더가 배포한 헤더·툴체인 | 데이터시트, RM, TRM, CMSIS 헤더, GCC 매크로 |
| **C** | 2차 자료 (커뮤니티, 재게시본) | 교차 확인 필요 |
| **D** | 계산·추정 | 유도 과정을 함께 기재 |

**A 등급이 B 등급과 충돌하면 A가 맞다.** 이 폴더에는 실제로 그런 사례가 여럿 있다
(QSPI 부품, 동작 주파수, 이더넷 PHY 주소 등 — 아래 "문서와 어긋난 지점" 참조).

## 조사 방법

네 갈래로 나누어, 서로를 교차 검증할 수 있게 했다.

### 1. ST-LINK 레지스터 판독 — 펌웨어 없이 실리콘에 직접 묻기

`code/stlink_dump.py`. STM32CubeProgrammer CLI의 임의 주소 읽기(`-r`, `-r32`)로
코어 사설 영역(PPB), 팩토리 프로그램 영역, 페리페럴 레지스터를 통째로 떠 온다.
**51개 영역 중 50개 성공** (실패한 1개가 그 자체로 정보다 — 아래 참조).

두 가지 상태에서 각각 떴다:
- `--mode HOTPLUG` — 기존 SNN 펌웨어가 **실행 중**인 상태. 그 펌웨어가 무엇을 설정해 두었는지 보인다.
- `--mode UR` — **리셋 직후** 상태. 하드웨어 리셋 기본값이 보인다.

두 덤프를 비교하면 **어떤 값이 실리콘 고정값이고 어떤 값이 소프트웨어 설정인지** 갈라진다.

### 2. 온디바이스 프로브 펌웨어 — 칩이 스스로를 측정하게 하기

`code/fw_hwprobe/`. 외부에서 관측할 수 없는 것들을 칩 자신이 재게 한다.

측정 결과는 두 경로로 나간다:
- USART1 (PA9/PB7) → ST-LINK 가상 COM 포트 → 실시간 확인
- **0x20040000의 고정 주소 결과 버퍼** → 실행이 끝난 뒤 ST-LINK로 통째 회수

두 번째 경로가 주력이다. 시리얼 타이밍이나 드롭에 좌우되지 않고, 펌웨어가 도중에 죽어도
그때까지 쌓인 로그를 건질 수 있다. 버퍼 선두의 매직값(`PRB1` 실행 중 / `PRBD` 정상 종료)으로
측정이 실제로 끝났는지 판별한다. 초기화 단계에서 멈추는 경우에 대비해 `0x2004BF80`에
진행 단계 번호를 남기고, 폴트가 나면 `0x2004BF00`에 폴트 상태 레지스터를 기록한다.

측정 모듈:

| 모듈 | 측정 대상 |
|---|---|
| `probe_regs.c` | 코어·캐시·TCM·FPU·MPU·디버그·팩토리·클럭·페리페럴 레지스터 전수 덤프와 해석 |
| `probe_mem.c` | 각 메모리의 **실제 크기**(aliasing 실측), 대역폭, 레이턴시, 캐시 효과 |
| `probe_cpu.c` | 명령어 처리량, DSP/FPU, **코드 배치별 실행 속도**, 200 vs 216 MHz |
| `probe_analog.c` | ADC로 **공급 전압·다이 온도**, TIM 입력 캡처로 **LSI/LSE 실제 주파수** |
| `probe_i2c.c` | I2C 버스 전 주소 스캔 → 실장된 칩 발견, 터치 컨트롤러 ID 확정 |
| `probe_board.c` | 오디오 코덱·이더넷 PHY의 ID 레지스터 판독, 물리 입력 핀 상태 |
| `probe_ext.c` | SDRAM/QSPI 초기화, **QSPI 플래시 JEDEC ID로 부품 확정** |

### 3. 호스트 측 정보 — 툴체인과 벤더 헤더가 아는 것

`code/collect_host_side.py`. 컴파일러가 이 타깃에 대해 켜는 아키텍처 기능 매크로
(`__ARM_FEATURE_DSP` 등)와, ST가 배포한 CMSIS 헤더에 박혀 있는 IRQ 번호표·페리페럴
베이스 주소를 추출한다. 벤더가 직접 기술한 값이므로 데이터시트와 같은 급으로 취급한다.

### 4. 공식 문서 조사, 그리고 실측과의 대조

`docs/`. DS10916(데이터시트), RM0385(레퍼런스 매뉴얼), PM0253, UM1907(보드 매뉴얼),
ES0290(에라타), ARM DDI 0489(Cortex-M7 TRM) 등을 주제별로 조사했다.
각 사실에 문서번호와 섹션을 붙였고, A/B 등급 주장은 별도 검증을 거쳤다.

**그다음, 9편 전부를 위 실측과 하나하나 대조했다.** 각 문서 맨 앞에
`## 이 보드 실측과의 대조` 절이 있고, 세 갈래로 나뉜다:

- **실측으로 확인됨** — 문서 예측값과 실측값을 나란히 적었다.
  `CCSIDR = 0xF003E019` 같은 값은 비트 단위로 맞았고, 계산으로 추정했던 [D] 등급 항목
  일부는 실측으로 확인되어 **[A]로 승격**되었다.
- **실측과 어긋남** — 문서 쪽을 신뢰하면 안 되는 항목. 본문 해당 위치에도
  `> **실측 정정**:` 인용 블록을 붙여 두었다. 원래 서술은 지우지 않았다 —
  문서가 왜 그렇게 적혔는지도 기록으로서 가치가 있기 때문이다.
- **아직 측정하지 않음** — 측정할 방법이 있는데 하지 않은 항목과 그 방법.

따라서 `docs/`를 읽을 때는 **맨 앞의 대조 절을 먼저 보고 본문으로 들어가야 한다.**

## 재현 방법

```bash
cd info/code

# 1) ST-LINK 레지스터 덤프 (보드 연결 필요, 펌웨어 불필요)
python3 stlink_dump.py --mode HOTPLUG --tag hotplug
python3 stlink_dump.py --mode UR      --tag reset --skip-cache-ids

# 2) 덤프 해석 문서 생성
python3 decode_dump.py

# 3) 호스트 측 정보
python3 collect_host_side.py

# 4) 온디바이스 프로브 (빌드 → 플래싱 → 결과 회수)
python3 run_probe.py

# 5) 측정이 끝나면 원래 SNN 펌웨어로 복원
python3 run_probe.py --restore
```

> **주의**: 4번은 보드의 플래시를 덮어쓴다. 측정 전 플래시 전체가
> `raw/flash_backup_1M.bin`에 백업되어 있고, `--restore`로 원래 펌웨어를 되돌릴 수 있다.

## 핵심 결과

상세는 [`raw/measured_facts.md`](raw/measured_facts.md)에 있다.
아래는 이 조사에서 나온 것 중 **알고 있던 것과 달랐거나, 이 프로젝트에 직접 영향을 주는** 항목이다.

### 문서와 어긋난 지점 — 실측이 아니었으면 몰랐을 것들

| 항목 | 흔히 알려진 것 | **이 보드의 실측** |
|---|---|---|
| 동작 주파수 | 216 MHz (F746의 최대치) | **200 MHz** (PLLN=400) |
| Flash wait state | 7 WS (216 MHz 기준) | **6 WS** |
| QSPI 플래시 부품 | Micron N25Q128A (`0x20BA18`) | **Winbond (`0xEF4018`)**, 16 MB |
| L1 캐시 용량 | 16 KB + 16 KB로 오인되는 경우가 많음 | **4 KB + 4 KB** |
| ITCM 크기 | ITCMCR.SZ를 TRM 표로 읽으면 8 MB | **16 KB** (0x00004000부터 폴트) |
| **ADC 캘리브레이션 주소** | `0x1FF07A4A` (STM32F4 계열 주소) | **`0x1FF0F44A`** |
| 이더넷 PHY 주소 | HAL 설정 헤더에 `DP83848_PHY_ADDRESS 0x01` | **LAN8742A, 주소 0** |
| `0xE0042000` | CTI (ARM 일반 주소맵) | **DBGMCU** (ST가 다르게 매핑) |
| 프레임버퍼 | RGB565 255 KiB/장으로 상정 | **ARGB8888 더블버퍼 (총 ≈1.0 MB)** |
| 페리페럴 IRQ 개수 | 98개 (번호 최댓값 기준) | **97개** — **IRQ 79번이 결번** |
| TPIU/ETM | ROM table이 present=0으로 광고 안 함 | **물리적으로 존재** (PIDR 0x9A9 / 0x975) |
| ST-LINK 보드 식별 | `Board: STM32F7508-DK`로 보고됨 | Flash 크기 레지스터가 **1024 KB** → F746NG |

**ADC 캘리브레이션 주소**가 실용적으로 가장 위험합니다. 잘못된 주소를 써도 폴트가 나지 않고
값도 그럴듯해 보여서, 온도·전압 계산이 조용히 틀립니다.

**보드 리비전 확정**: QSPI가 Winbond인 것으로 이 보드는 **MB1191-F746NGH6-C-03 (`$CU4`)** 임이 확정됐다.
문서가 PCB 실크로 확인하라며 열어 둔 분기를 JEDEC ID 실측이 닫았다.

### 이 프로젝트(SNN 추론)에 직접 영향을 주는 발견

1. **ART Accelerator가 꺼진 채로 돌고 있었다.**
   `FLASH_ACR = 0x00000006` (LATENCY=6, PRFTEN=0, ARTEN=0).
   원인은 `ImageClassification/Core/Inc/stm32f7xx_hal_conf.h:150`의 `PREFETCH_ENABLE 0U`와
   `ART_ACCLERATOR_ENABLE` 매크로 부재다. 정의되지 않은 매크로는 `#if`에서 0으로 평가되므로
   `HAL_Init()`이 ART를 영영 켜지 않는다.

2. **그런데 이 칩은 옵션 바이트에 의해 ITCM 별칭(0x00200000)에서 부팅한다** (`BOOT_ADD0 = 0x0080`).
   Cortex-M7의 L1 I-cache는 **AXIM 경로에만** 적용되고, ITCM 경로는 **ART가 담당**한다.
   즉 `SCB_CCR.IC = 1`로 I-cache를 켜 두었어도 **명령어 페치에는 아무 캐시도 걸려 있지 않았다.**

3. **그 손해를 실제 코드 실행으로 측정했다.** 같은 기계어를 여러 위치에서 돌린 결과
   (커널이 I-cache 4 KB를 넘는 조건):

   | 실행 조건 | cyc/insn | ITCM 대비 |
   |---|---|---|
   | ITCM-RAM (이론 상한) | 0.50 | 1.00× |
   | ITCM별칭 + **ART ON** | 0.89 | 1.78× |
   | **ITCM별칭 + ART OFF** ← 현재 조건 | **1.26** | **2.52×** |
   | FLASH AXIM + I-cache OFF (최악) | 1.89 | 3.78× |

   → **`ARTEN` 비트 하나를 켜면 1.42배**, 코드를 ITCM RAM에 올리면 **2.52배** 개선된다.
   단, 커널이 4 KB 안에 들어가면 배치를 바꿔도 차이가 없다(작은 커널에서는 모두 0.53 cyc/insn).

4. **동작 주파수가 200 MHz다.** 기존 SNN 실험 수치(4,494 / 9,641 / 2,407 ms)는
   216 MHz가 아니라 200 MHz에서 측정된 것이다.
   (논문 `paper_ieie/`는 이미 200 MHz로 정확히 기재되어 있다.)
   216 MHz로 올려도 플래시 wait state가 6→7로 오르므로 **플래시에서 실행되는 코드는 이득이 거의 없다.**
   TCM에 머무는 계산만 클럭에 비례해 1.08배 빨라진다.

5. **D-cache가 4 KB뿐이다.** 워킹셋이 4 KB를 넘는 순간 포인터 체이싱 레이턴시가
   2.0 사이클에서 7~9 사이클로 급변한다. SNN 커널의 타일 크기를 정할 때 이 값이 기준이 되어야 한다.
   SRAM1에서 D-cache를 끄면 int16 MAC 처리량이 0.52 → 0.13 MAC/cycle로 **4배** 떨어진다.

6. **데이터를 어디에 두는지가 크게 좌우한다.** DTCM 복사가 1,421 MB/s(7.11 bytes/cycle)로
   SRAM1(696 MB/s)의 2.0배다. 그리고 **LDM/STM이 LDR/STR보다 1.55배 빠르다.**

7. **int16 SIMD 이득은 1.33배**다 (SMLAD 0.52 vs 스칼라 C 0.39 MAC/cycle, DTCM 기준).
   이론 피크 2.0 MAC/cycle에 못 미치는 이유는 SMLAD 하나가 워드 2개를 읽어야 해서
   **로드 대역폭이 상한을 결정**하기 때문이다. 계산이 아니라 공급이 병목이다.

### 데이터시트에 있을 수 없는, 이 개체 고유의 값

| 항목 | 실측 |
|---|---|
| 공급 전압 VDDA | **3.311 V** |
| 다이 온도 | **35.7 ~ 41.1 °C** (동작 중 상승) |
| LSI 실제 주파수 | **26,652 Hz** (공칭 32 kHz 대비 **-16.7 %**) |
| LSE 실제 주파수 | **32,765 Hz** → 32.768 kHz 크리스탈 실장 확인 |
| Unique device ID | `330034000850435436303520` |
| microSD 카드 | **삽입되어 있음** (PC13 = 0) |

LSI 편차가 -16.7 %나 된다는 점은 실용적으로 중요하다. IWDG 타임아웃을 공칭 32 kHz로 계산하면
실제로는 그만큼 길어진다.

### 측정 과정에서 알아낸 하드웨어 동작 특성

- **`PWR_CSR1.VOSRDY`는 SYSCLK이 HSI로 도는 동안 셋되지 않는다.** VOS를 설정한 뒤 이 플래그를
  기다리도록 코드를 짜면 그 자리에서 영구히 멈춘다 (PC=0x08000EE8에서 정지하는 것을 확인).
  ST의 HAL도 이 플래그를 기다리지 않으며, over-drive는 **PLL이 lock된 뒤에** 켜야 한다.
- **MPU를 설정하지 않으면 SDRAM(0xC0000000)은 Device 메모리다.** D-cache에 캐싱되지 않고,
  비정렬 접근은 `CCR.UNALIGN_TRP`과 무관하게 **항상 UsageFault**다.
- **프로빙 중 PRIMASK를 세우면 BusFault도 마스킹되어 HardFault로 승격된다.**
  존재하지 않는 페리페럴 주소를 안전하게 읽으려면 인터럽트를 끄지 말아야 한다.
