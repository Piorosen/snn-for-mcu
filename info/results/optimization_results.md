# SNN 추론 최적화 결과 — 상세 기록 (2026-07-27)

`info/` 하드웨어 실측 조사를 근거로 ImageClassification SNN 추론을 단계적으로 최적화한
전체 기록이다. 각 단계마다 **무엇을, 왜 그렇게 바꿨고, 실측이 무엇을 보여줬으며,
그 결과를 어떻게 해석해야 하는지**를 남긴다. 예측이 빗나간 단계(ART, ITCM)도 그대로
기록했다 — 왜 빗나갔는지가 이 문서에서 가장 재사용 가치가 높은 부분이기 때문이다.

- 대상: STM32F746G-DISCO, 200 MHz (over-drive), T=30 타임스텝, CIFAR-10
- 측정일: 2026-07-27, 도구: DWT_CYCCNT (1사이클 해상도)
- 재현: `python3 info/code/run_snn_bench.py`

## 1. 측정 방법론

### 1.1 벤치 하네스 (main_bench.cc, `SNN_BENCH=ON`)

애플리케이션 `main.cc`는 SD카드 읽기 → JPEG 디코딩 → LCD 출력 → 추론이 섞여 있고,
시간도 HAL_GetTick(1 ms 해상도)으로 잰다. 논문 수치(V3 = 2,407 ms)도 그 조건에서
나왔다. 최적화 효과를 흔들림 없이 재려면 추론 외 요소를 전부 제거해야 하므로:

- 입력은 플래시에 박아 둔 CIFAR-10 테스트셋 8장 (`snn_bench_images.c`, 자동 생성).
  SD/JPEG/LCD가 측정에 전혀 개입하지 않는다.
- 인코딩 RNG는 시드 고정 xorshift32 → 같은 바이너리를 다시 돌리면 사이클 수까지
  거의 그대로 재현된다.
- 시간은 DWT_CYCCNT. 워밍업 1장(캐시·분기예측 냉간, lazy 초기화)은 측정에서 제외.
- 결과는 `g_snn_bench` 구조체에 남고 ST-LINK HOTPLUG 메모리 판독으로 회수한다.
  시리얼이 없으므로 타이밍·드롭 문제가 없다.
- 각 측정은 **당시의 `FLASH_ACR`/`SCB_CCR` 레지스터 값을 함께 기록**한다. "ART를 켠
  빌드"라는 라벨이 아니라 실리콘이 답한 값(v0: `0x006`, 이후: `0x306`)으로 조건을
  증명한다. ITCM 복사 바이트 수(`itcm_code_bytes`)도 같은 목적이다.

v0(2,328.5 ms)가 논문 V3(2,407 ms)보다 3.3% 빠른 이유는 조건 차이다: 논문 측정은
타임스텝 루프 안에 LCD 문자열 출력이 포함되어 있었고, 입력 이미지·시계 해상도도
다르다. 따라서 **이 문서의 모든 비교는 같은 하네스 안의 상대 비교**만 사용한다.

### 1.2 회귀 검증 — spike_checksum

모든 최적화는 "더 빠르되 계산은 동일"해야 한다. 근사가 아니라 **비트 단위 동일**을
요구했고, 이를 기계적으로 검증하는 장치가 `spike_checksum`이다:

```
매 타임스텝, 10개 출력 스파이크에 대해: chk += (uint32_t)(uint16_t)s_spk_out[i]
→ 8장 × 30스텝 × 10출력 = 2,400개 값의 누적 합
```

단순한 합이지만 민감도는 매우 높다. LIF 뉴런은 막전위가 30스텝에 걸쳐 누적되는
상태 기계라서, 네트워크 어디서든 중간값이 1 LSB만 달라져도 발화 시점이 바뀌고,
그 차이가 다음 레이어·다음 스텝으로 연쇄돼 출력 스파이크 패턴이 달라진다.
dense SMLALD 경로와 희소 sum-of-weights 경로, TFLM 경로와 직접 경로, 다섯 가지
메모리 배치가 전부 같은 checksum을 낸다는 것은 전 구간 정수 파이프라인이 완전히
동일하게 동작한다는 뜻이다. (한계: 8장 × 30스텝이 실행한 경로에 대한 증명이다.
합산이라 상쇄 우연이 이론상 가능하지만, 예측 8개 일치와 결합하면 실용상 충분하다.)

### 1.3 사후 검증

구현 후 별도의 적대적 리뷰(10개 에이전트: 3개 관점 리뷰 → 발견 항목별 반박 시도)를
돌렸다. 추론 코드에서는 결함이 나오지 않았고, 벤치 하네스에서 3건이 확인되어 수정했다
(§8). 측정 수치는 수정 후 재측정한 확정값이다.

## 2. 단계 1 — v0: 기존 조건 재현 (2,328.5 ms, 기준선)

모든 `SNN_OPT_*`를 끄면 코드 경로·메모리 배치가 기존 HEAD와 동일해지도록 만들었다
(빈 링커 섹션, dense 커널, 아레나 256 KB, `FLASH_ACR=0x006`). 기준선의 레이어 분해:

| 구간 | ms/이미지 | 비중 | 스텝당 일량 |
|---|---|---|---|
| CPL1 (Conv1+Pool+LIF1) | 446.0 | 19.2% | 884,736 MAC |
| CPL2 (Conv2+Pool+LIF2) | 1,828.0 | 78.5% | 4,718,592 MAC |
| FC + TFLM 디스패치 | ≈16.4 | 0.7% | 40,960 MAC |
| encode (rate coding) | 35.4 | 1.5% | 3,072 원소 |
| 입력 memcpy | 1.9 | 0.1% | 6,144 B |
| LIF_out | 0.07 | — | 10 뉴런 |

총 일량은 5.64M MAC/스텝 × 30스텝 = **169.3M MAC/이미지**. 2,328.5 ms로 나누면
유효 처리량 **72.7 MMAC/s** — 이 칩의 SMLAD 이론 피크(400 MMAC/s)의 18%다.
이 갭(5.5×)이 최적화의 총예산이고, CPL2가 전체의 78.5%이므로 승부처다.

## 3. 단계 2 — ART accelerator + 프리페치: **효과 0** (예측 실패 ①)

### 무엇을 했나

`stm32f7xx_hal_conf.h`의 `PREFETCH_ENABLE`/`ART_ACCELERATOR_ENABLE`을 1로 게이트
(`SNN_OPT_ART`). `HAL_Init()`이 `FLASH_ACR`에 ARTEN|PRFTEN을 세운다. 측정 기록의
`FLASH_ACR`이 `0x006 → 0x306`으로 바뀐 것으로 적용을 확인했다.

### 왜 효과를 기대했었나

`info/raw/measured_facts.md` §8: 기존 펌웨어는 ART가 꺼진 채였고(`ARTEN=0`), 이
보드는 옵션 바이트(`BOOT_ADD0=0x80`)로 ITCM 별칭(0x00200000)에서 부팅한다. ITCM
경로 플래시는 I-cache 대상이 아니고 ART가 캐싱을 담당하므로, "명령 페치에 아무
캐시도 없다 → ART 한 비트로 1.42배"가 조사의 결론이었다.

### 실측: 2,328.5 → 2,328.9 ms (변화 없음, 측정 노이즈 이내)

### 왜 빗나갔나 — 부팅 주소와 실행 주소는 다르다

조사가 놓친 것: **부팅이 ITCM 별칭에서 시작해도, 실행 주소는 링커가 정한다.**
이 프로젝트의 링커 스크립트는 FLASH를 0x08000000(AXIM)에 두므로, 리셋 벡터에 적힌
주소부터 모든 함수 주소가 0x08xxxxxx다. 즉 첫 벡터 페치 한 번만 ITCM 경로를 지나고,
이후 **모든 명령 페치는 AXIM 경로 → L1 I-cache(4 KB)가 담당**한다. ART는 ITCM 경로
전용이라(실측: AXIM 대역폭은 ART ON/OFF에 159.96 MB/s로 무반응 — measured_facts §2.2)
이 조건에서는 만질 수 있는 것이 없다. `info/README.md`의 "페치에 캐시가 전혀 없었다"는
결론은 ITCM 별칭 실행을 전제한 것이었고, 실제 조건은 "AXIM + I$ 4KB"였다.

### 그래도 켜 둔 이유

에라타 없음이 확인됐고(ES0290 Rev 7에 플래시 인터페이스/ART 항목 자체가 없다),
코드를 ITCM 별칭으로 재링크하는 선택지를 열어 두며, 끌 이유가 하나도 없다.
비용 0의 보험이다.

## 4. 단계 3 — 핫 커널 코드 ITCM RAM 배치: **효과 0** (예측 실패 ②)

### 무엇을 했나

- 링커에 `ITCMRAM (16K @ 0x00000000)` 영역과 `.itcm_code` 섹션(LMA=플래시,
  VMA=ITCM)을 추가. 부팅 시 `snn_itcm_init()`(snn_tcm.c)이 플래시 적재분을 복사한다.
- `SNN_ITCM_CODE` 매크로(= `section(".itcm_code") + noinline`)를 추론 핫 함수 전부에
  부착. noinline은 마킹 안 된 플래시 상주 호출자에 인라인되어 배치가 무효화되는 것을
  막는다 (LTO는 인라인된 코드를 **호출자의** 섹션에 둔다).
- 최종 full 빌드의 ITCM 내용 (nm 실측, 총 4,936 B / 16 KB):

| 심볼 | 크기 |
|---|---|
| sparse_row_sums (LTO 특수화) | 1,964 B |
| build_nz_idx_win (〃) | 970 B |
| snn_lif_s16 | 476 B |
| spiking_rate | 368 B |
| snn_convolve_pool_lif_s16 / CplEvalImpl | 352 + 352 B |
| LifOutEval / Cpl1·2Eval | 316 + 80 B |
| 롱브랜치 베니어 7개 (ITCM↔플래시 왕복, 자동 생성) | 56 B |

베니어까지 섹션 안에 배치되므로 복사 범위에 포함된다 — 이 확인이 중요했다.

### 왜 효과를 기대했었나

실측 조사에서 "큰 커널(6,144 B, I$ 4 KB 초과)은 ITCM-RAM 0.50 cyc/insn vs 플래시
2.52×"였다. 핫셋 추정치(~6 KB)가 I$를 넘으므로 스래싱을 예상했다.

### 실측: 2,328.9 → 2,331.2 ms (변화 없음)

### 왜 빗나갔나 — "핫셋 6 KB"가 아니라 "핫루프 수백 B"였다

프로브의 "큰 커널" 시나리오는 6 KB 전체를 균일하게 순회하는 코드다. 실제 추론은
다르다: 시간의 대부분이 dense SMLALD 내적 루프(수십 B)와 그 주변(수백 B)에서 돈다.
그 정도는 4 KB I-cache에 여유 있게 상주하고, 실측 조사 자신도 "작은 커널은 어디에
두든 0.53 cyc/insn"이라고 말하고 있었다. 즉 **명령 페치는 애초에 병목이 아니었다.**
이 결과는 뒤 단계의 해석을 정리해 준다 — 남은 병목은 전부 데이터 쪽이다.

### 부수 확보물 (이 단계의 실제 가치)

- 이후 희소 커널(§6)이 ITCM에서 돌게 되는 기반. 희소 경로는 분기·간접 인덱싱이
  많아 dense보다 코드가 크고 접근 패턴이 불규칙하므로, ITCM 상주는 최소한 해가 없고
  I$를 데이터 경합 없이 다른 코드에 양보한다.
- 구현 중 두 개의 실전 함정을 발견해 해결했다 (재발 주의):
  1. **링커 심볼을 `extern uint32_t` 스칼라로 선언하면 안 된다.** LTO가 "서로 다른
     객체의 주소 비교"를 UB로 보고 복사 루프의 바이트 카운트를 0으로 접었다
     (복사는 수행되는데 반환값만 0이 되는 실제 오컴파일을 관측). `extern char x[]`
     배열 선언 + `memcpy`가 올바른 관용구다.
  2. **벤치 펌웨어는 `__WFI()`로 잠들면 안 된다.** 이 보드는 `DBGMCU_CR=0`
     (DBG_SLEEP=0)이라 슬립 중 SWD 접속이 불가능해져, 측정이 끝나 있는데도 호스트가
     결과를 영영 못 읽는다. busy 스핀으로 대기해야 한다.
- ITCM 복사 후 캐시 유지보수는 불필요하다(TCM은 캐시 대상이 아니고 ART는 플래시
  전용) — DSB/ISB로 충분. `info/docs/02_cache_tcm.md` §3.3의 결론이 그대로 적용됐다.

## 5. 단계 4 — 데이터 DTCM/SRAM 배치: **+6.9%** (2,331.2 → 2,178.7 ms)

### 무엇을 어디로 옮겼나

TFLM 경로의 데이터는 원래 두 곳에 있었다: 가중치는 flatbuffer(플래시 rodata,
200,232 B) **안**, 활성값·LIF 상태·스크래치는 256 KB 아레나(SRAM) 안. 이를 커스텀
오퍼의 Prepare 단계에서 재배치했다 (TFLM 내부는 건드리지 않는다 — Prepare/Eval이
우리 코드라서 가능한 우회다):

| 데이터 | 크기 | 원래 위치 | 새 위치 | 근거 |
|---|---|---|---|---|
| conv1 가중치 | 6,912 B | 플래시 flatbuffer | **DTCM** (사본) | 매 스텝 전량 128회 재독 |
| conv2 가중치 | 147,456 B | 플래시 flatbuffer | **SRAM1 .bss** (사본) | DTCM 64 KB에 불가; D$ 적중 시 SMLAD 0.52 MAC/cyc로 DTCM과 동일(실측), 미스 비용은 플래시의 절반 이하 |
| LIF 상태 (mem+spk_prev ×3층) | 49,192 B | 아레나(SRAM) | **DTCM 풀** | 매 스텝 전량 읽고 씀 |
| im2col 스크래치 | 4,608 B | 아레나(SRAM) | **DTCM** | 커널 안 최다 접근 버퍼 |
| 텐서 아레나 | 256 KB | SRAM | **64 KB로 축소** | 위 항목들이 빠져나가 실사용 79,764 → 25,940 B |

배치는 링커의 `.dtcm_bss (NOLOAD)` 섹션으로 한다. 이 섹션을 평평한 320 KB RAM
영역의 **선두**에 두면 자동으로 DTCM(0x20000000~0x2000FFFF)에 떨어지고, 링크 타임
`ASSERT(_edtcm_bss <= 0x20010000)`가 예산 초과를 잡는다. `SNN_OPT_DTCM`이 꺼진
빌드에서는 섹션이 비어 레이아웃이 기존과 완전히 같다 — v0의 재현성이 유지되는 이유다.

안전성 검토: SD카드는 폴링 모드라 DMA가 없고(BSP `_DMA` 변형은 미호출), 설령 DMA를
쓰더라도 F7의 DMA는 AHBS 포트로 DTCM에 닿는다. LIF 상태는 `snn_reset_state()`가
이미지마다 memset하므로 NOLOAD(제로 초기화 없음)여도 안전하다 — 이 두 가지는
적대적 리뷰에서도 공격받았고 반박으로 종결됐다.

### 실측: CPL1 451.1 → 401.8 (-10.9%), CPL2 1,824.7 → 1,719.8 (-5.7%)

### 해석 — 왜 7%에 그쳤나

dense SMLALD 루프는 매 반복 가중치 2쌍+활성값 2쌍을 로드한다. conv2 기준 가중치
트래픽은 스텝당 147,456 B × 32타일 = **4.7 MB**, 이미지당 141 MB다. 이 스트림의
공급원이 플래시(AXIM, D$ 경유 ~305–360 MB/s)에서 SRAM1(D$ 경유, 미스 레이턴시
8–9 cyc vs 플래시 ~14 cyc)로 바뀐 만큼만 빨라진다. 144 KB가 4 KB D-cache를 계속
갈아엎는 구조 자체는 그대로이기 때문에 라인필 횟수는 줄지 않는다. **트래픽의 총량을
줄이지 않는 한 배치 개선의 상한이 이 정도**라는 것이 이 단계의 교훈이고, 그 총량을
줄이는 것이 다음 단계다.

(conv1이 conv2보다 개선율이 높은 것은 가중치 6.9 KB가 통째로 DTCM에 들어가
라인필이 0이 되기 때문이다.)

## 6. 단계 5 — 희소 spike-driven 커널: **지배적 효과** (2,178.7 → 380.6 ms, 단독 5.7×)

### 6.1 수학적 근거와 비트 동일성

이 네트워크의 **모든 conv 입력은 이진**이다. 소스 레벨로 확인된 사실이다:

- CPL1 입력: rate 인코더 출력 ∈ {0, 32767} (snn_encode.c)
- CPL2 입력: LIF1 스파이크 ∈ {0, spike_val} (snn_lif_s16.c는 0 또는 spike_val만 쓴다)
- 패딩 = 0 = 비발화와 동일

입력이 {0, S}이면 내적이 붕괴한다:

```
Σₖ w[k]·x[k]  =  S · Σ_{x[k]≠0} w[k]
```

MAC이 "활성 인덱스의 가중치 덧셈"으로 바뀐다. 발화율이 곧 일량이다: **입력 47.7%,
LIF1 4.1%** (호스트 실험 실측) — CPL2에서는 연산의 ~96%가 "0과의 곱"이었던 것이다.

비트 동일성 논증:
1. Σw는 int32로 안전: |Σw| ≤ rhs_cols·max|w| = 1152·508 = 585,216 ≪ 2³¹.
2. S·Σw는 int64로 계산: dense의 int64 누산과 같은 값. 이후 `+ bias64 →
   arm_nn_requantize_s64 → clamp → LIF`는 dense와 **같은 함수, 같은 순서**.
3. int32 랩어라운드 덧셈은 결합·교환이 성립하므로 합산 순서 변경(전치·블로킹)은
   결과에 영향이 없다. 패딩 셀은 0이라 목록에서 빠지는 것과 항등.
4. 최종 증명은 계산이 아니라 실측: spike_checksum이 dense 경로와 비트 일치.

### 6.2 다섯 번의 반복 — 각 단계에서 배운 것

희소 커널은 한 번에 나온 것이 아니라 보드 실측으로 5회 반복 개선한 결과다.
전 과정에서 checksum은 한 번도 어긋나지 않았다.

| 반복 | 내용 | ms/img | CPL1 | CPL2 |
|---|---|---|---|---|
| (직전) dtcm | dense SMLALD | 2,178.7 | 401.8 | 1,719.8 |
| k1 | 인덱스 목록 + 2채널 레지스터 블로킹 | 579.2 | 253.9 | 298.8 |
| k2 | im2col 제거 (윈도우 직접 인덱싱) | 504.3 | 228.7 | 249.5 |
| k3 | 가중치 전치 + 메모리 누산 배열 | 457.5 | **282.8 ▲** | 148.4 |
| k4 | 전치 + 8채널 레지스터 블로킹 | 382.2 | 223.2 | 132.9 |
| k5 | conv1 인덱스 생성 branchless + 하네스 정비 | **380.6** | 222.1 | 132.2 |

**k1 — 기본형 (dtcm 대비 3.8×).** im2col 컬럼을 스캔해 비영 인덱스 목록
(uint16, DTCM)을 만들고, 채널 2개씩 가중치 행에서 `w[idx]`를 모아 더한다.
CPL2가 1,720 → 299 ms로 떨어지며 가설이 실증됐다.

**k2 — im2col 자체를 제거 (-75 ms).** 희소 경로는 컬럼의 **값**이 필요 없다 —
전부 S이므로 **위치**만 있으면 된다. 그래서 im2col로 컬럼을 실체화(conv2 기준
매 스텝 147 KB 쓰기+읽기)한 뒤 스캔하는 대신, 입력 윈도우에서 직접 인덱스를
생성했다 (`build_nz_idx_win`). 인덱스 산식 `k = (ky·kw + kx)·Ci + c`가 im2col
컬럼 레이아웃과 동일하므로 합의 집합이 같다 → 비트 동일. 부수 효과로 커널의
스크래치 버퍼 의존이 사라졌다.

**k3 — 가중치 전치: CPL2엔 정답, CPL1엔 역효과 (교훈이 담긴 단계).**
k2까지의 남은 병목은 가중치 gather의 캐시 거동이었다. 원래 레이아웃
`w[co][k]`에서 한 채널 행은 2,304 B(=72 캐시라인)인데 활성 인덱스는 그중
~47곳에 흩어진다. 라인당 16개 가중치 중 1개만 쓰고 버리는 셈이라, 144 KB
가중치에서 라인필이 양산된다. 전치 `wT[k][co]`로 바꾸면 **활성 인덱스 1개의
전 채널(64ch = 128 B = 4라인)이 연속**이 되어 가져온 라인을 전부 사용한다.
CPL2: 249.5 → 148.4 ms.

그런데 CPL1은 228.7 → 282.8 ms로 **악화**됐다. 원인: conv1 가중치는 6.9 KB로
이미 DTCM에 있어 **절감할 캐시 미스가 애초에 없는데**, k3 구현이 채널 64개
누산기를 레지스터에 못 담아 메모리 배열(`sums[64]`)에 두는 바람에 원소당
load-add-store 3연산이 추가됐다. "캐시 지역성 개선"과 "레지스터 상주"를 맞바꾼
것이 미스가 없는 층에서는 순손실이었다.

**k4 — 8채널 레지스터 블로킹으로 양쪽을 다 잡음 (-75 ms).** 전치 레이아웃을
유지하되 채널을 8개 블록으로 잘라 누산기 8개를 전부 레지스터에 상주시켰다.
인덱스당 가중치 16 B(8ch)를 32비트 페어 로드 4회 + SXTAH(부호확장+가산,
GCC가 `(int16_t)(pair>>16)` 캐스트에서 생성) 8회로 처리한다. 인접 블록 쌍이
같은 캐시라인(32 B = 16ch)을 나눠 쓰므로 라인 재사용도 남는다.
CPL1 282.8 → 223.2 (k2보다 좋아짐), CPL2 148.4 → 132.9 ms.

**k5 — conv1 인덱스 생성 branchless (-1 ms, 기대 이하).** conv1 입력 밀도는
47.7%라 원소별 `if (src[c] != 0)` 분기가 사실상 동전 던지기 → 미스프레딕션
비용을 의심해 "항상 쓰고 조건부로 카운터만 증가"하는 branchless append로
바꿨다. 실측 개선은 1 ms에 그쳤다 — 컴파일러가 이미 조건부 실행으로 처리하고
있었거나, 이 구간이 생각보다 작았다는 뜻이다. 가설이 기각된 기록으로 남긴다.
(conv2 쪽 스캔은 32비트 페어 `pair==0` fast path를 유지 — 밀도 4%에서는 이
분기가 96% 한 방향이라 예측이 잘 맞고, branchless보다 빠르다.)

### 6.3 층별 비대칭 — 발화율이 이득의 상한이다

| | 밀도 | dense(dtcm) | 희소(최종) | 배율 |
|---|---|---|---|---|
| CPL2 | **4.1%** | 1,719.8 ms | 132.2 ms | **13.0×** |
| CPL1 | 47.7% | 401.8 ms | 222.1 ms | 1.8× |

희소화의 이득은 정확히 희소성에 비례한다. CPL1은 절반이 활성이라 스캔·인덱스
생성 오버헤드를 빼면 이득 여지가 작고, 최종 프로파일에서 **최대 항목(222 ms,
전체의 58%)으로 남았다**. 남은 여지는 §10.

### 6.4 인코더 LUT 캐시 (35.4 → 5.9 ms)

`spiking_rate()`는 매 호출 256개 발화 임계값을 double로 재계산했는데, double은
이 FPU(단정밀도 전용)에서 소프트플로트라 그 자체로 스텝당 수만 사이클이었다.
(gain, offset)이 바뀌지 않으면 표가 결정적으로 동일하므로 캐시했다. 임계값
비트가 같으니 스파이크 시퀀스도 비트 동일. 이미지당 30회 재계산이 1회(첫 호출)로
줄어 인코딩이 6배 빨라졌다. 남은 5.9 ms는 원소당 xorshift+비교(92,160회/이미지)의
본질 비용이다.

## 7. TFLM 오버헤드 — 380.6 vs 372.8 ms (2.1%)

같은 최적화를 직접 퓨전 경로(`SNN_USE_TFLM=OFF`, snn.c)에도 적용해 측정했다.
차이 7.8 ms가 TFLM 인터프리터(그래프 순회, 노드 디스패치, 텐서 관리)의 비용이다.
주목할 것은 **두 경로의 spike_checksum까지 일치**한다는 점: LIF1 스파이크 진폭이
다른데도(직접 경로 Q14=16384, TFLM 경로 Q15=32767 — 배율이 requantize 계수에
흡수되는 설계) 최종 출력이 비트 단위로 같다. 퓨전 정수 파이프라인의 일관성에 대한
독립 증거다. 희소 커널의 `in_spike_val` 파라미터가 이 차이를 정확히 전달한다.

## 8. 하네스에 대한 적대적 리뷰 결과 (수정 3건, 반박 4건)

**수정한 3건** (모두 하네스, 추론 코드 아님):

1. **측정 중 1 kHz IRQ가 살아 있었다.** 벤치는 SysTick TICKINT를 껐지만 이
   프로젝트의 HAL 타임베이스는 SysTick이 아니라 **TIM6**이다. 측정 창마다 ~380회의
   ISR 진입이 섞이고 있었다 → `HAL_NVIC_DisableIRQ(TIM6_DAC_IRQn)` 추가. 수치
   영향은 ~0.1%로 상대 비교에는 무해했지만 "인터럽트 없는 측정"이라는 하네스의
   전제가 거짓이었다.
2. **사이클 누산기가 uint32 한계의 87%.** v0의 8장 합계가 3.73G 사이클로, 조금만
   느린 구성(Debug 빌드, T 증가)이면 조용히 랩되어 엉터리 기준선을 만들 수 있었다
   → 64비트 누산으로 변경.
3. **`--fetch-only`가 첫 변형의 심볼 주소만 사용.** `.dtcm_bss`가 .bss를 밀어내서
   변형마다 `g_snn_bench` 주소가 ~60 KB 다르다 → 빌드된 모든 변형의 주소를 짚어
   magic이 맞는 것을 자동 선택하도록 수정.

**반박으로 종결된 4건**: NOLOAD로 인한 LIF 상태 제로화 상실(→ `snn_reset_state()`가
이미지마다 memset하므로 무해), 같은 주장의 변형 1건, 주소 0의 ITCM 코드가 NULL 포인터
쓰기에 무방비(→ 기존 MPU 구성에서도 동일했던 조건이며 커널 손상 시 checksum이 잡는다),
snn_accel_init 실패 경로의 풀 누수(→ 실패 시 재시도 자체가 없는 구조).

## 10. 재현 방법과 남은 여지

```bash
# 애플리케이션 (전체 최적화 기본 ON) — 보드에 플래시된 상태
cmake -S ImageClassification -B ImageClassification/build-opt -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE=ImageClassification/cmake/arm-none-eabi.cmake -DCMAKE_BUILD_TYPE=Release
cmake --build ImageClassification/build-opt

# 벤치 매트릭스 전체 (빌드→플래시→회수→회귀검증)
python3 info/code/run_snn_bench.py
```

옵션: `SNN_OPT_ART/ITCM/DTCM/KERNEL`(기본 ON), `SNN_BENCH`, `SNN_USE_TFLM`.
원시 데이터: `info/results/snn_bench_results.json` (레이어별 사이클, 상태 레지스터 포함).

**남은 여지 (미적용, 예상 효과 순):**

1. **CPL1 이벤트 기반 재구성** (현재 222 ms, 전체의 58%): 인코더가 스파이크를 쓰는
   시점에 좌표 목록을 함께 방출하면, 출력 픽셀마다 윈도우를 재스캔(입력을 스텝당
   ~9회 재독)하는 현재 구조를 입력 1회 순회로 바꿀 수 있다. 정수 합은 순서 무관이라
   비트 동일성 유지 가능. 다만 밀도 47.7%에서는 상한이 ~2× 남짓이다.
2. **FC 가중치 SRAM 사본** (~18 ms 잔여의 일부): 현재 flatbuffer(플래시) 상주.
   TFLM 내장 FC 오퍼라 우회에는 커스텀 등록이 필요하다.
3. **216 MHz 승격** (+8% 상한): over-drive는 이미 활성이라 PLLN=432와 7 WS 전환만
   필요. TCM/SRAM 상주 작업만 클럭에 비례 가속. 논문 조건(200 MHz)과의 비교
   가능성 때문에 보류했다.
4. **SDRAM MPU 속성**: 현재 write-through인데 Cortex-M7 r0p1 에라타 1259864(Cat A,
   WT store→load 손상)의 조건에 해당한다. 추론 데이터는 SDRAM을 쓰지 않아 이번
   작업과 무관하지만, LCD 프레임버퍼 경로를 손볼 일이 있으면 WBWA 전환(+ 그리기 후
   clean)을 함께 검토할 것.
