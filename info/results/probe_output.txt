== 칩 내부 아날로그 실측 (이 개체 고유값)
================================================================
팩토리 캘리브레이션 값:
  VREFINT_CAL @0x1FF0F44A = 1492  (3.3V, 30'C 에서 측정된 VREFINT ADC 코드)
  TS_CAL1     @0x1FF0F44C = 942  (30'C)
  TS_CAL2     @0x1FF0F44E = 1195  (110'C)

VREFINT 측정 코드 = 1486 (12비트, 64회 평균)
→ VDDA = 3.313 V   ; 이 보드에 지금 실제로 걸린 아날로그 공급 전압

온도센서 측정 코드 = 968 (12비트, 64회 평균)
→ 다이 온도 = 39.16 'C  (VDDA 보정 후 코드 971)
   공식: T = 80/(TS_CAL2-TS_CAL1) * (TS_DATA*VDDA/3.3 - TS_CAL1) + 30

VBAT 측정 코드 = 1022 → VBAT = 3.306 V (내부 1/4 분압 보정 후)
   주: 이 보드에 백업 배터리가 없으면 VBAT은 VDD에 묶여 있다.

== 저속 발진기 실측 (LSI / LSE)
================================================================
LSI: LSIRDY=1
→ LSI 실측 = 26652 Hz  (공칭 32000 Hz, TIM5 타이머클럭 100000000 Hz 기준)
   공칭 대비 편차 -16.7 %  ; RC 발진기라 개체·온도별로 크게 흔들린다

LSE: 시도 전 LSEON=1, 기동 후 LSERDY=1 (BDCR=0x00000003)
→ LSE 실측 = 32743 Hz (공칭 32768 Hz) ; 32.768kHz 크리스탈이 실장되어 있다

HSE: 현재 HSEON=1 HSERDY=1 HSEBYP=0
   HSEBYP=0 이면 크리스탈 발진 모드, 1이면 외부 클럭 입력 모드다.
   주: SYSCLK이 HSE 기반 PLL로 돌고 있으므로 HSE를 껐다 켜는 실험은 하지 않는다.

== I2C 버스 스캔 (보드에 실장된 칩 실측)
================================================================
각 주소에 START+주소를 보내고 ACK가 돌아오는지로 판정한다.
주소는 7비트/8비트 표기를 함께 적는다 (8비트 = 7비트 << 1).

--- I2C3 (PH7=SCL, PH8=SDA, AF4 — 오디오 코덱·터치 컨트롤러 계열) ---
  응답: 7비트 0x1A (8비트 0x34)  → WM8994 오디오 코덱 (AUDIO_I2C_ADDRESS)
  응답: 7비트 0x38 (8비트 0x70)  → FT5336 정전식 터치 컨트롤러 (TS_I2C_ADDRESS)
  총 2개 장치가 응답했다.
  BSP 헤더에 정의된 주소별 응답 여부:
    0x34 응답 WM8994 오디오 코덱 (AUDIO_I2C_ADDRESS)
    0x70 응답 FT5336 정전식 터치 컨트롤러 (TS_I2C_ADDRESS)
    0x60 무응답 카메라 모듈 (CAMERA_I2C_ADDRESS, 보통 미장착)
    0xA0 무응답 EEPROM A01 (EEPROM_I2C_ADDRESS_A01)
    0xA6 무응답 EEPROM A02 (EEPROM_I2C_ADDRESS_A02)

--- I2C1 (PB8=SCL, PB9=SDA, AF4 — Arduino 확장 커넥터) ---
  응답한 장치 없음.
  BSP 헤더에 정의된 주소별 응답 여부:
    0x34 무응답 WM8994 오디오 코덱 (AUDIO_I2C_ADDRESS)
    0x70 무응답 FT5336 정전식 터치 컨트롤러 (TS_I2C_ADDRESS)
    0x60 무응답 카메라 모듈 (CAMERA_I2C_ADDRESS, 보통 미장착)
    0xA0 무응답 EEPROM A01 (EEPROM_I2C_ADDRESS_A01)
    0xA6 무응답 EEPROM A02 (EEPROM_I2C_ADDRESS_A02)

터치 컨트롤러 식별 (I2C3 0x70):
  reg 0xA8 = 0x51   ; 칩 ID (FT5336_CHIP_ID_REG) — FT5336이면 0x51
  reg 0xA6 = 0x12   ; 펌웨어 버전 (FT5336_FIRMID_REG)
  reg 0xA3 = 0x6F   ; 패널 ID
  reg 0xAF = 0xEA   ; 릴리스 코드
  reg 0xA1 = 0x99   ; 라이브러리 버전 하위 바이트
  → 칩 ID가 0x51이므로 이 보드의 터치 컨트롤러는 FT5336으로 확정된다.

== 보드 주변 부품 실측 (ID 레지스터·핀 상태)
================================================================

오디오 코덱 식별 (I2C3 0x34):
  reg 0x0000 (칩 ID) = 0x8994
  → 0x8994이므로 오디오 코덱은 WM8994로 확정된다.

이더넷 PHY 식별 (MDIO: PA2=MDIO, PC1=MDC):
  PHY 주소 0: ID1=0x0007 ID2=0xC131
      OUI=0x0001F0  모델=0x13  리비전=0x1
      → SMSC/Microchip LAN8742A 계열로 식별된다.
      BMCR=0x3000 BMSR=0x7809  링크=down, 자동협상=미완료

보드 입력 핀 상태:
  PC13 (SD_DETECT) = 0  → microSD 카드 삽입됨
  PI11 (사용자 버튼 B1) = 0  → 눌리지 않음
  PI1  (LED1/LD1) 은 이 펌웨어가 진행 표시용으로 출력 구동 중
  PI12 (LCD_DISP), PK3 (LCD 백라이트) 는 LCD를 초기화하지 않아 건드리지 않았다

LTDC (LCD-TFT 컨트롤러) 현재 레지스터:
  SSCR=0x00000000 BPCR=0x00000000 AWCR=0x00000000 TWCR=0x00000000 GCR=0x00000000
  → 타이밍 레지스터가 비어 있다. 이 펌웨어는 LCD를 초기화하지 않는다.

== 메모리 서브시스템 실측
================================================================
SYSCLK 200000000 Hz 기준. 반복 3회의 최솟값을 쓴다 (최솟값이 노이즈가 가장 적다).
측정 하네스 오버헤드 17 cyc. run_min()과 완전히 같은 경로(인자 셋업 + 함수 포인터
  간접 호출 blx + 커널 프롤로그/에필로그 + dsb/isb + CYCCNT 2회 읽기)로 쟀고,
  아래 3~5·7·8절의 모든 수치에서 뺐다. 6절은 기준선이 다르므로 그 절에 따로 적었다.
I-cache: 진입 시 OFF → 이 모듈이 도는 동안 강제로 ON (CCR.IC=1), 종료 시 원복.
측정 중 인터럽트는 PRIMASK로 차단한다. 폴트 복구용 벡터테이블을 0x20001000에 임시 설치했다.
버퍼 배치: ITCM 0x00001960(4 KB) DTCM 0x20001200(32 KB) SRAM1 0x20016C80(64 KB) SRAM2 0x2004C000(8 KB)

[메모리 속성 / MPU 상태 - 측정 시작 시점]
  MPU_TYPE = 0x00000800  (DREGION = 8개 지원, IREGION = 0)
  MPU_CTRL = 0x00000000  → MPU 꺼져 있음 → ARMv7-M 기본 메모리맵이 그대로 적용된다
  기본 메모리맵 속성 (ARMv7-M ARM Table B3-1):
    0x00000000 ITCM / FLASH_ITCM 별칭 : Normal WT (Code)
    0x08000000 FLASH_AXIM          : Normal WT (Code)
    0x20000000 DTCM / SRAM1 / SRAM2 : Normal WBWA (SRAM)
    0x40024000 BKPSRAM             : Device (Peripheral)
    0x90000000 QSPI 메모리맵       : Normal WT (RAM)
    0xC0000000 SDRAM               : Device, non-shareable
  단, ITCM(0x00000000~0x00003FFF)과 DTCM(0x20000000~0x2000FFFF)은 TCM 인터페이스
  직결이라 위 속성과 무관하게 애초에 D-cache 대상이 아니다.
  → SDRAM(0xC0000000)은 기본맵에서 Device다. Device 메모리는 CCR.DC와 무관하게
     D-cache에 캐싱되지 않고, CCR.UNALIGN_TRP와 무관하게 비정렬 접근이 항상
     UsageFault다. 그래서 4·5·7·8절은 SDRAM에 한해 MPU 리전 0으로 8MB를
     Normal WBWA(non-shareable)로 재정의한 조건을 함께 재서 나란히 비교한다.
     측정이 끝나면 MPU를 다시 끈다 (마지막 절에서 확인 출력).
외부/백업 메모리 실측 판정: SDRAM=사용 가능  QSPI=사용 가능  BKPSRAM=사용 가능

== 1. 메모리 영역 실제 크기 실측 (aliasing / 폴트 경계 탐색)
================================================================
방법: 기준 주소에 표식을 쓰고 2^k 오프셋마다 다른 값을 써 본 뒤 기준을 다시 읽는다.
      기준값이 바뀌면 되감김(WRAP), 쓴 값이 유지되지 않으면 없는 메모리(DEAD),
      버스 폴트면 FAULT. 첫 실패 지점은 1KB 단위 이분 탐색으로 좁혔다.
      읽기 전용 영역(FLASH/QSPI)은 쓰기 시험이 불가하므로 '읽어서 폴트가 나는
      첫 주소'만으로 상한을 잡는다 (되감김은 이 방법으로 구분되지 않는다).
      D-cache는 이 시험 동안 OFF다 (캐시가 되감김을 가려 버린다).

region       base        DS크기     실측크기   판정   경계에서
---------------------------------------------------------------
ITCM         0x00001960     16 KB     16 KB  FAULT +0x00002800 에서 FAULT  [일치]
DTCM         0x20001200     64 KB    320 KB  FAULT +0x0004F000 에서 FAULT  [불일치]
SRAM1        0x20016C80    240 KB    256 KB  FAULT +0x00039400 에서 FAULT  [불일치]
SRAM2        0x2004C000     16 KB     16 KB  FAULT +0x00004000 에서 FAULT  [일치]
BKPSRAM      0x40024000      4 KB      4 KB  FAULT +0x00001000 에서 FAULT  [일치]
SDRAM        0xC0000000   8192 KB   8192 KB  FAULT +0x00800000 에서 FAULT  [일치]
FLASH_AXIM   0x08000000   1024 KB   1024 KB  FAULT +0x00100000 에서 FAULT  [일치]
FLASH_ITCM   0x00200000   1024 KB   1024 KB  FAULT +0x00100000 에서 FAULT  [일치]
QSPI         0x90000000  16384 KB  16384 KB  FAULT +0x01000000 에서 FAULT  [일치]

주의: DTCM(0x20000000+64K) - SRAM1(0x20010000) - SRAM2(0x2004C000)은 주소가 연속이라
      쓰기 시험만으로는 서로의 경계가 드러나지 않는다 (되감김이 없다). 각 영역의 실측값은
      '그 주소에서 위로 얼마나 더 실재하는 메모리가 이어지는가'로 읽어야 하며,
      물리적 경계는 아래 2번의 접근 지연 스캔이 갈라 준다.

================================================================
== 2. 접근 지연으로 본 물리 경계 (주소가 연속인 영역 구분)
================================================================
같은 주소 공간이라도 물리적으로 다른 메모리면 접근 비용이 다르다.
아래는 D-cache OFF 상태에서 32B 간격 읽기의 접근당 사이클이다 (루프 오버헤드 포함).

[0x20000000 대역] 4 KB 간격 접근 지연 스캔 (D-cache OFF, 32B 스트라이드 읽기)
  0x20000000 - 0x2000FFFF :   2.19 cyc/접근
  0x20010000 - 0x2004FFFF :   8.19 cyc/접근
  0x20050000 - 0x20053FFF : 접근 불가 (버스 폴트)

[0x00000000 대역] 1 KB 간격 접근 지연 스캔 (D-cache OFF, 32B 스트라이드 읽기)
  0x00000000 - 0x00003FFF :   2.19 cyc/접근
  0x00004000 - 0x00005FFF : 접근 불가 (버스 폴트)

참고: 스트라이드 루프 자체의 오버헤드는 1.98 cyc/회 다 (위 값에 포함되어 있다).

write32 = STR x8, write64 = STRD x4, writeSTM = STM 8레지스터 x2,

== 4. D-cache 상태별 비교 (콜드 상태: 매 측정 전 clean+invalidate)
================================================================

각 행의 [ ] 안이 그 측정 동안 실제로 적용된 메모리 속성이다. 캐시 대상이 아닌
속성(TCM / Device)에서는 세 열이 같게 나오는 것이 정상이며, 그 차이 없음은
'캐시 정책의 차이가 작다'는 뜻이 아니라 '애초에 캐싱되지 않는다'는 뜻이다.

(라벨이 조건과 일치함을 증명한다).

  - 'SDRAM [map:Device]' 행의 세 열이 같은 이유는 캐시 정책 차이가 없어서가 아니라
    Device 메모리라 CCR.DC=1이어도 D-cache에 한 줄도 올라가지 않기 때문이다.
    (DC 열이 0/1/1로 찍혀 있는데도 값이 같다는 점이 바로 그 증거다.)

== 6. 플래시 접근 특성 (AXIM 별칭 vs ITCM 별칭, ART ON/OFF)
================================================================
측정 루프는 .itcm_code 섹션에 올려 ITCM에서 실행한다. 그래야 ART/캐시를 꺼도
코드 페치 경로가 흔들리지 않고 데이터 접근만 순수하게 측정된다.
워킹셋 64 KB. FLASH_AXIM=0x08000000, FLASH_ITCM=0x00200000 (같은 물리 플래시의 다른 경로)
기준선: 이 표의 값에서는 ITCM 계측 프레임 오버헤드 13 cyc(dsb/isb + CYCCNT 2회 읽기)를
  뺐다. 위 3~5절의 run_min 기준선과 같은 방식이다. 다만 두 기준선 모두 루프 제어
  (포인터 증가 + subs + bne) 비용은 포함한 채로 남아 있으므로, 접근당 사이클을
  절대값으로 읽을 때는 2절 끝에 찍힌 루프 오버헤드를 함께 보아야 한다.

AXIM         WB       ON        304.74 MB/s     1.52 B/cyc     14.24 cyc/접근

== 7. 외부 메모리 (SDRAM / QSPI)
================================================================
[SDRAM] 보드 실장 SDRAM (FMC SDRAM bank1, 0xC0000000). 크기는 1절에서 실측했고,
        버스폭/CAS 지연/클럭은 이 절에서 재지 않았다 (FMC 레지스터 덤프 절 참조).
  아래 세 블록의 대비가 이 칩 메모리 시스템의 핵심이다:
   - map:Device  = MPU 미설정 시의 기본 메모리맵. Device라 D-cache를 켜도 캐싱되지 않는다.

  즉 첫 블록과 셋째 블록의 차이가 곧 'MPU 설정만으로 얻는 SDRAM 성능'이다.
  copyLDM은 읽기+쓰기 합산 규약이다.

== 8. 정렬 페널티 (32비트 로드)
================================================================
모두 64B 간격으로 접근해 접근당 라인 상황을 같게 맞췄다 (D-cache WB, 워킹셋 64KB).
SRAM1은 Normal WBWA라 비정렬 접근이 합법이다. SDRAM은 기본맵에서 Device이고,
Device 메모리의 비정렬 접근은 CCR.UNALIGN_TRP와 무관하게 항상 UsageFault이므로
그대로는 잴 수 없다. 그래서 이 표의 SDRAM 열은 MPU 리전 0으로 SDRAM 8MB를
Normal WBWA로 재정의한 상태에서 쟀다. 그럼에도 모든 측정을 폴트 가드 안에서
돌리므로, 폴트가 나면 그 칸만 '측정 불가(폴트)'로 표시되고 진행은 계속된다.

측정 조건 증명: CCR.DC=1, CACR.FORCEWT=0, CCR.UNALIGN_TRP=0, SDRAM 속성=MPU r0: Normal WBWA, non-shareable

정렬 조건                   SRAM1 [Normal WBWA]     SDRAM [MPU:Normal WBWA]
-----------------------------------------------------------------------------
4B 정렬 (라인 내부)      9.01 cyc/접근         19.12 cyc/접근
+1B 어긋남 (라인 내부)  13.01 cyc/접근       측정 불가(폴트)
+2B 어긋남 (라인 내부)  13.01 cyc/접근       측정 불가(폴트)
라인 경계 걸침 (+30B)   20.01 cyc/접근       측정 불가(폴트)
라인 경계 걸침 (+31B)   20.01 cyc/접근       측정 불가(폴트)

== 메모리 측정 마무리
================================================================
가드 구간에서 잡아낸 버스 폴트 34회 (전부 복구했다). 마지막 CFSR=0x01000000
MPU 원복 확인: MPU_CTRL=0x00000004 (진입 시 0x00000000), 리전 0 RASR=0x00000000 → MPU 꺼짐 - SDRAM은 다시 기본맵 Device로 돌아갔다.
이 절의 모든 수치는 CPU 로드/스토어 기준이다. DMA / DMA2D / LTDC 경로는
AHB 마스터가 달라 대역폭 특성이 다르며, 여기서 측정하지 않았다.
또한 모든 측정은 인터럽트 차단(PRIMASK=1) 상태에서 3회 반복 최솟값이다.
I-cache 원복: CCR.IC=1 → 0 (진입 시 상태로 되돌렸다)

== CPU 1) 클럭 실측 검증 - DWT_CYCCNT가 정말 HCLK로 도는가
================================================================
RCC_CFGR         @ 0x40023808 = 0x0000940A  ; SW/HPRE/PPRE
RCC_PLLCFGR      @ 0x40023804 = 0x09406419  ; PLLM/N/P/SRC
레지스터 역산 : SRC=HSE 25000000 Hz, PLLM=25 PLLN=400 PLLP=2
              VCO=400000000 Hz -> SYSCLK=200000000 Hz, HPRE=/1 -> HCLK=200000000 Hz
실측         : 500 ms 동안 99999960 cycles -> HCLK = 200.000 MHz
SysTick RELOAD=200000 (=200000 사이클/tick), CTRL=0x00010007
역산 HCLK=200000 kHz, 실측 HCLK=200000 kHz, 차이=0 kHz (0.1% 이내 - 일치)
해석: DWT_CYCCNT와 SysTick은 둘 다 HCLK에서 파생되므로 이 비교는
      'CYCCNT가 HCLK를 1:1로 센다 + SysTick RELOAD가 SystemCoreClock과
      일치한다'를 확인한다. 절대 주파수의 근거는 보드의 25MHz HSE 크리스탈이며,
      위 PLL 역산값과 실측 사이클 수가 일치하면 그 경로 전체가 검증된 것이다.

== CPU 2) 명령어 스루풋 / 레이턴시
================================================================
보정 방식: 같은 본문을 1배/2배로 언롤한 두 함수를 재고 그 차분만 쓴다(기울기 방식).
           루프 제어(subs/bne)와 호출·DWT 프레임 비용은 두 측정에 똑같이 들어 있어
           차분에서 정확히 상쇄된다. 빈 루프 비용을 그대로 빼면 루프 제어가 payload와
           듀얼이슈되는 만큼 과잉보정이 되어 IPC가 상한 2.0을 넘을 수 있다.
측정 프레임 오버헤드(DWT 2회 읽기 사이): 28 cycles (차분에서 상쇄됨, 참고값)
빈 루프(subs+bne x 2000): 2007 cycles = 1.00 cyc/iter (참고값. 이 값을 빼지는 않는다)
보정 검증: payload가 없는 벤치의 1배/2배 차분 = 0 cycles (0이어야 정상)

[정수 ALU]
명령            스루풋[cyc/insn]  [insn/cyc]   레이턴시[cyc]
--------------  ----------------  ----------   -------------
NOP                         0.97        1.03               -
ADD imm                     1.88        0.53            1.88
ADD Rm,LSL#2                1.88        0.53            2.00
MUL                         1.50        0.67            2.00
MLA                         1.84        0.54            1.88
CLZ                         1.84        0.54            2.34
UDIV(어려움)               18.00        0.06               -
UDIV(쉬움)                  6.00        0.17               -
SDIV(어려움)               19.00        0.05               -
해석: 스루풋 0.5 cyc/insn = 매 사이클 2명령 발행(듀얼이슈 성공).
      레이턴시는 앞 결과를 뒤가 바로 쓰는 체인이라 파이프라인 깊이가 드러난다.
      나눗셈은 비파이프라인이라 스루풋=레이턴시이며 피연산자 크기에 비례해 느려진다.

--------------  ----------------  ----------   -------------

해석: LDM/STM은 명령 하나당 8워드를 옮기므로 cyc/word가 LDR보다 낮으면
      DTCM 인터페이스가 명령 발행이 아니라 데이터 폭으로 포화한 것이다.

[분기 예측]
예측 가능(방향 고정)          218016 cycles / 16000 branches = 13.63 cyc/분기(주변 명령 포함)
예측 불가(난수 조건)          435453 cycles / 16000 branches = 27.22 cyc/분기(주변 명령 포함)
차이                          13.59 cyc/분기 → 오예측률 50% 가정 시 오예측 페널티 ≈ 27.18 cycles
해석: 두 벤치는 명령열이 같고(단위마다 tst/조건분기/add.w/b 네 개가 반드시 실행됨)
      taken 비율도 둘 다 50%다. 예측 가능 버전은 절반을 beq(항상 taken),
      절반을 bne(항상 not taken)로 만들어 방향을 고정했다. 실행 명령 수도
      taken 비율도 같으므로 남는 차이는 예측 성공률뿐이고, 그 차이가 파이프라인
      리필 비용이다.

== CPU 4) 코드 배치별 실행 속도 - 같은 기계어를 네 곳에서 실행
================================================================
.itcm_code 섹션: ITCM 0x00000000, FLASH 적재 0x0802339C, ITCM별칭 0x0022339C, 6488 bytes
SRAM1 사본: 0x20012AC0 (6488 bytes 복사, CleanDCache+InvalidateICache 완료)
커널: 독립 ADD 2개를 번갈아 1536회(큰 커널 6144 bytes) / 32회(작은 커널 128 bytes)
      독립 명령이므로 ITCM에서는 듀얼이슈로 0.5 cyc/insn이 상한이다.
      즉 명령 페치가 8 bytes/cycle을 못 대면 그 즉시 병목이 보인다.

[작은 커널 128 bytes - I-cache(4KB)/ART(1KB)에 전부 들어간다]
실행 위치            I$   ART      cycles   cyc/insn   ns/insn   기준대비
-------------------  ---  ---   ---------   --------   -------   --------
ITCM-RAM             ON   ON        51017       0.53      2.65      1.00x
FLASH AXIM           ON   ON        51018       0.53      2.65      1.00x
FLASH AXIM           OFF  ON       216054       2.25     11.25      4.25x
FLASH ITCM별칭       ON   ON        51018       0.53      2.65      1.00x
FLASH ITCM별칭       ON   OFF      141025       1.47      7.35      2.77x
FLASH ITCM별칭       OFF  OFF      141042       1.47      7.35      2.77x

해석: 루프가 캐시/ART에 다 들어가면 어디에 놓든 차이가 거의 없다.
      "플래시에서 돌려도 안 느리던데"라는 착각은 대개 이 조건에서 나온다.

[큰 커널 6144 bytes - I-cache 4KB / ART 1KB를 넘긴다]
실행 위치            I$   ART      cycles   cyc/insn   ns/insn   기준대비
-------------------  ---  ---   ---------   --------   -------   --------
ITCM-RAM             ON   ON        49548       0.50      2.50      1.00x
FLASH AXIM           ON   ON       165942       1.69      8.45      3.38x
FLASH AXIM           OFF  ON       186181       1.89      9.45      3.78x
FLASH ITCM별칭       ON   ON        87373       0.89      4.45      1.78x

SRAM1                ON   ON       148397       1.51      7.55      3.02x
SRAM1                OFF  ON       160638       1.63      8.15      3.26x
해석: 여기서부터가 진짜다. 코드가 캐시보다 크면 명령 페치 경로가 그대로
      성능이 된다. ITCM은 64비트 폭 코어 직결이라 매 사이클 2명령을 대주지만,
      플래시는 6 wait state라 ART/I-cache가 없으면 페치가 곧 벽이 된다.

  이 보드의 기존 SNN 펌웨어는 VTOR=0x00200000, 즉 플래시의 ITCM 별칭에서
  실행되면서 ART(FLASH_ACR.ARTEN)가 꺼져 있었다. 위 표의 'FLASH ITCM별칭 /
  ART OFF' 행이 바로 그 조건이고, 'ITCM-RAM' 행이 이론적 상한이다.
  두 행의 비가 그 설정으로 잃고 있던 배수다. ARTEN 비트 하나로 회수된다.

== CPU 5) DWT 이벤트 카운터로 본 마이크로아키텍처
================================================================
카운터는 전부 8비트다(256에서 되감긴다). 그래서 구간을 200사이클 미만으로 잡는다.
CPICNT=추가 사이클, EXCCNT=예외 오버헤드, LSUCNT=로드/스토어 추가 사이클,
FOLDCNT=폴딩되어 0사이클로 처리된 명령 수.

워크로드                 CYC  CPI  EXC SLEEP  LSU FOLD   비고
--------------------  ------ ---- ---- ----- ---- ----   ------------------
정수 ADD (독립)          266   168     0     0     2    74   8비트 카운터 포화 가능 (cyc=266 > 255) → 수치 신뢰 불가
정수 ADD (종속)          335   183     0     0     2    20   8비트 카운터 포화 가능 (cyc=335 > 255) → 수치 신뢰 불가
LDR (DTCM)               243   146     0     0     2    75   대상명령 ~136개, CPI≈1.79
MUL                      354   192     0     0     4    13   8비트 카운터 포화 가능 (cyc=354 > 255) → 수치 신뢰 불가
분기 (예측 성공)         379    10     0     0     2    39   8비트 카운터 포화 가능 (cyc=379 > 255) → 수치 신뢰 불가
분기 (난수 조건)         391    21     0     0     2    38   8비트 카운터 포화 가능 (cyc=391 > 255) → 수치 신뢰 불가
해석: FOLD가 크면 그만큼의 명령이 공짜로 처리된 것이고(주로 분기/NOP),
      LSU가 크면 로드/스토어가 추가 사이클을 먹은 것이다. EXC가 0이 아니면
      측정 구간에 예외가 끼어든 것이므로 그 행은 버려야 한다.

== CPU 6) SNN 대표 커널 - int16 MAC 처리량
================================================================
벡터 길이 512개 int16(=1024 bytes) x 200회 = MAC 102400회
데이터 위치: DTCM 0x20000400 / SRAM1 0x200126A0
이 절 진입 시 SCB->CCR=0x00060200 (D-cache OFF, I-cache ON)
각 행의 CCR.DC 열은 그 행을 측정하는 동안 읽은 실제 캐시 상태다(라벨의 근거).

커널 / 데이터 위치                   cycles    MAC/cyc       GOPS   CCR.DC
--------------------------------  ---------   --------   --------   ------
SMLAD  (32b누산) / DTCM              195412       0.52       0.21   1
SMLALD (64b누산) / DTCM              196013       0.52       0.21   1
스칼라 C int32   / DTCM              260014       0.39       0.16   1
SMLAD  (32b누산) / SRAM1 D$ON        195412       0.52       0.21   1
스칼라 C int32   / SRAM1 D$ON        260014       0.39       0.16   1
SMLAD  (32b누산) / SRAM1 D$OFF       809824       0.13       0.05   0
스칼라 C int32   / SRAM1 D$OFF      1488426       0.07       0.03   0
절 종료 시 SCB->CCR=0x00060200 (진입 시 상태로 복구)
주: DTCM(0x20000000)은 코어 직결 TCM이라 애초에 D-cache 대상이 아니다.
    위 DTCM 행의 CCR.DC=1은 '조건을 고정했다'는 뜻일 뿐 캐시가 개입한다는 뜻이 아니다.

SIMD 이득(DTCM 기준): SMLAD / 스칼라 = 1.33배
이론 피크(레지스터 상주, SMLAD 1 cyc/insn 가정): 2.00 MAC/cycle = 0.80 GOPS @ 200 MHz
해석: 실측이 2.00 MAC/cycle에 못 미치는 만큼이 로드 비용이다. SMLAD 한 개는
      워드 2개(가중치+입력)를 읽어야 하므로, 로드 포트가 한 사이클에 한 워드면
      MAC/cycle의 상한은 로드 쪽에서 결정된다. DTCM에 두면 wait state가 0이라
      이 상한에 가장 가깝다. SRAM1은 AXI를 타므로 D-cache 유무가 그대로 드러나는데,
      그 크기는 위 표의 'SRAM1 D$ON' 행과 'SRAM1 D$OFF' 행의 비(CCR.DC 열이 1과 0인
      두 행)가 말해 준다. 미리 단정하지 말고 그 두 행을 직접 비교하라.

== CPU 7) 200MHz vs 216MHz
================================================================
클럭 전환 완료: SYSCLK=216000000 Hz(레지스터 역산 216000000 Hz), PCLK2=108000000 Hz, USART1_BRR=938, FLASH_ACR=0x00000307
FLASH wait state = 7 WS (200MHz에서는 6 WS)

200MHz로 복귀: SYSCLK=200000000 Hz, USART1_BRR=868

항목                        200MHz            216MHz            비(216/200)
------------------------  ---------------   ---------------   -----------
정수 ADD 스루풋                0.50 cyc/insn      0.50 cyc/insn    1.00x   (2.50 ns → 2.31 ns)
SMLAD MAC/cycle(DTCM)          0.52 MAC/cyc       0.52 MAC/cyc     1.00x
DTCM 읽기                      7.31 B/cyc         7.31 B/cyc       1.00x
SRAM1 읽기                     2.24 B/cyc         2.24 B/cyc       1.00x
FLASH AXIM 코드                1.70 cyc/insn      1.77 cyc/insn    1.04x   (8.50 ns → 8.19 ns)

같은 값을 절대 성능으로 환산 (사이클이 아니라 시간 기준):
항목                        200MHz            216MHz            비
------------------------  ---------------   ---------------   -----------
SMLAD 절대 처리량               104 MMAC/s           112 MMAC/s     1.08배
DTCM 읽기 대역폭               1462 MB/s            1579 MB/s       1.08배
SRAM1 읽기 대역폭               448 MB/s             484 MB/s       1.08배
FLASH 코드 1명령 시간          8.50 ns               8.19 ns          0.96배
해석: 216MHz는 플래시 wait state가 6→7로 올라간다. 그래서 플래시에서 코드를
      페치하는 항목은 사이클 기준으로 오히려 나빠질 수 있고, 클럭이 8% 올라간
      만큼을 그대로 못 가져간다. 반대로 TCM/레지스터에만 머무는 계산은 클럭에
      정확히 비례해 1.08배가 나온다. 코드를 ITCM/RAM에 올려두지 않은 채
      216MHz로 올리면 기대만큼 빨라지지 않는다는 뜻이다.

== CPU 8) 종합 - 이 칩의 실측 성능 요약
================================================================
이 보드의 STM32F746NGH6(Cortex-M7 r0p1)는 200MHz에서 다음과 같이 측정되었다. 독립적인 정수 명령을 나란히 놓으면 IPC 0.53 명령/사이클이 나와, 실제로 in-order 2-way 듀얼이슈로 동작함이 확인된다. DSP 확장의 SMLAD는 1.84 cyc/insn으로 발행되어 레지스터 상주 조건에서 int16 MAC 2.00회/사이클이 상한이고, 데이터를 DTCM에 두고 실제로 로드까지 포함해 돌리면 0.52 MAC/cycle, 즉 0.21 GOPS(1 MAC = 2 OP)가 실효 성능이다. 같은 계산을 스칼라 C로 쓰면 0.39 MAC/cycle에 그쳐 SIMD 이득은 1.33배다. 코드 배치의 영향은 캐시에 안 들어가는 크기의 루프에서 최대 3.78배로, ITCM 실행 대비 ART 꺼진 플래시 실행이 그만큼 손해다. 병목은 명령어 실행이 아니라 공급 쪽이다: 명령은 플래시 페치 경로(ART/I-cache)에서, 데이터는 SRAM1의 AXI 왕복(D-cache 유무)에서 막힌다. SNN 추론처럼 가중치를 순차적으로 훑는 워크로드는 계산이 아니라 이 두 공급 경로를 어떻게 배치하느냐로 성능이 결정된다.
